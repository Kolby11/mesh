# 2026-07

Newest first. Append-only — see [`README.md`](README.md).

## 2026-07-31 — remove the unused Luau `ChunkCache`

area: frontend scripting, hot reload

Removed the unbounded global source-string cache and its reload invalidation
path. `compile_and_execute` always passed the original source to mlua and
production never read a cache entry, so the cache provided no compilation
reuse while retaining old source versions under an unchecked FNV-64 key.

**Verified.** `cargo test -p mesh-core-scripting --lib` and `cargo check -p
mesh-core-shell` pass.

## 2026-07-31 — Luau `mesh.i18n.t()` uses the active locale catalog

area: frontend scripting, localization

`require("mesh.i18n")` and `import("mesh.i18n", "t")` now resolve keys through
the owning module's effective catalog rather than returning the raw key. A
script context retains a small module-scoped catalog snapshot; new component
runtimes receive it before `init()`, and locale changes replace it in every
live context. Existing imported `t` functions see the replacement, so plain
script variables such as the navigation settings tooltip update on the next
script evaluation. Missing keys still return the key, preserving the existing
visible-miss behavior.

**Verified.** `cargo test -p mesh-core-scripting --lib` (180 passed, 27
ignored), `cargo test -p mesh-core-locale --lib` (3 passed), and `cargo check
-p mesh-core-shell` passed. The scripting regression covers both `require` and
named `import`, plus an already-imported function after a catalog refresh; the
locale regression checks module-catalog precedence over global locale entries.

## 2026-07-31 — Named shell profiles switch composition and preferences live

area: shell composition, module runtime, settings, CLI

Profiles are now complete runtime composition boundaries rather than startup
filters. Their `settings` namespaces layer over shared defaults, root keys are
real surface/Luau/storage instance identities, and multiple instances of one
frontend module can mount together with independent placement and preferences.
The same resolution path is used at startup and during live switching.

Switching validates the candidate graph and settings, compiles and mounts new
roots off-screen, and starts changed service providers without publishing them.
Identical providers remain running. Only after every candidate provider reports
ready does the shell atomically save `active-profile`, reveal the new roots,
publish changed providers, apply theme/locale/runtime preferences, and remove
orphans. A frontend mount error, invalid graph, missing requirement, or backend
initialization failure aborts the staged objects and leaves the old pointer,
surfaces, providers, and settings intact. Updates emitted by prepared providers
are ignored until commit.

`mesh-shell profile use <id>` requests the transaction over the private shell
IPC socket and falls back to selecting the next startup when no shell runs.
`profile set/unset` writes sparse scoped preferences, and provider selections
made through settings now persist in the active profile rather than leaking
into the legacy root graph.

**Verified.** `cargo test -p mesh-core-module --lib`: 156 passed, 3 ignored.
Focused shell gates passed: 6 profile-matching tests, all 7 module-config tests,
the IPC profile-switch parser, and the installed-graph debug snapshot. The full
shell run reached 588 passed, 122 ignored, and 17 failures; one was a stale
Material Symbols fixture assertion corrected here. The remaining 16 are the
pre-existing renderer/interaction failures already carried by this tree (real
surface geometry, retained restyle, input, and icon proof tests), unrelated to
profiles. `cargo test -p mesh-tools-cli` passes (no unit cases).

## 2026-07-30 — `filter: blur()` blurs the subtree, not the box

area: rendering, retained display list, painter, settings

`filter: blur()` parsed and stored fine and had, until now, one effect: the
node's own background rectangle was drawn through a Skia mask filter. Its text,
its icons, and every descendant painted sharp on top of a fuzzy backing plate —
which is not what any stylesheet author means by blur.

The fix is the lowering the plan called for. A node with a blur radius now
emits `PushFilterLayer` before its own paint command and `PopFilterLayer` after
its children and scrollbars, so the whole subtree rasterizes into one offscreen
that is blurred and composited as a unit. The push carries the region the layer
covers: the node's visual bounds (which `visual_clip_for` already padded by the
kernel reach) unioned with the descendants' bounds grown by that same pad, so
the blur spills past the element box instead of stopping at a hard edge. The
per-shape `PainterPaint::filter` lane and its helpers are gone — keeping both
would have blurred the background twice.

Three things had to follow the layer, because a layer is not a command:

- **Layers outlive a command buffer.** A subtree's paint spans many
  `execute_commands_in_session` calls, so the open-layer stack moved out of the
  execute loop's locals onto the engine, with `close_painter_layers` unwinding
  anything a clipped replay left open.
- **Partial repaint may not split a scope.** A blurred subtree is now one
  atomic command span; `widen_selection_to_layer_scopes` also grows any
  selection that overlaps part of a scope, and the multi-region replay path
  falls back to one pass per region when the stream has scopes at all.
  Replaying half a layer would either drop the push (painting the subtree
  sharp) or drop the pop (leaking the layer into later commands).
- **Damage is layer-shaped.** Every pixel of a blur depends on the others, so
  `filter_layer_regions` joins the backdrop read regions in what is now
  `expand_damage_for_blur_regions`: damage anywhere inside a layer grows to the
  whole layer.

The immediate painter (`render_tree*`, still used by tests and the rotation
path) got the same semantics by the route that fits it — rasterize the subtree
into its own `PixelBuffer` and composite it back through a blur image filter —
so the two painters no longer disagree about what `filter` means.

Nesting is capped at four layers deep; beyond that the subtree paints unblurred
with a painter diagnostic, because each level is an offscreen allocation plus a
blur pass over it.

In-surface `backdrop-filter` is deliberately untouched: it stayed
compositor-owned in the 2026-07-16 delegation and this change gives no new
reason to revisit that.

**Quality is configurable** through `shell.render.blur` — `passes` (1–3) and
`max_radius` — read at settings load and reload and pushed into the painter.
A `downscale` knob was prototyped alongside them and dropped on the
measurements; see `performance-log.md`.

**Verified.** New tests cover the lowering (a child's commands land inside the
scope, with a padded push region), scope-atomic selection, layer-shaped damage
expansion, the nesting cap, and — the point of the whole exercise — a pixel
assertion that a *child's* edge mixes into its parent across the boundary and
that the blur spills outside the element box. Under `nix develop`,
`cargo test -p mesh-core-render` is green at 200 tests; `mesh-core-shell` holds
at the same 18 failures as `main`, name for name. `mesh-core-render`'s test
build was also broken at `main` (11 `SharedWidgetChildren` type errors left by
the memo structural-sharing commit) and is fixed here.

## 2026-07-30 — two-finger trackpad scroll turns the bubble ring

area: shared bubble options, language popover, theme selector, interaction

The bubble stage bound only `onscroll`. Trackpad input arrives with
`AxisSource::Finger`, which the presentation layer routes to a separate
`twofingerscroll` event, so two-finger scrolling over the bubbles reached no
handler at all and nothing rotated. The stage now binds both events to the same
caller prop.

The two are not interchangeable: a wheel sends one event per notch, a trackpad
a continuous stream of small pixel deltas. Feeding the raw stream to the ring
would spin it, so each caller runs its scroll deltas through a `scroll_step`
helper that passes wheel events straight through and accumulates trackpad
travel, spending one step per 40px and dropping banked travel on a direction
reversal. The helper is duplicated in the language popover and the theme
selector because a prop-passed handler is *not* a callable Lua value — the
compiler resolves it to an element handler reference — so `BubbleOptions`
cannot notch centrally and then invoke its caller. Attempting that is what the
first version of this change got wrong.

Regression: `shipped_language_popover_rotates_on_two_finger_trackpad_scroll`
drives three sub-notch deltas and asserts the ring holds still, then crosses the
notch and asserts it turned exactly one slot.

**Verified.** Under `nix develop`, `cargo test -p mesh-core-shell` holds at 18
failures against the 20-failure in-flight baseline. `cargo fmt --check` and
`git diff --check` pass. The 40px notch is a guess at a comfortable trackpad
feel and has not been tried on real hardware.

## 2026-07-30 — the bubble ring rotates around its arc instead of sliding

area: shared bubble options, interaction

The first scroll rotation translated all three bubbles by the same vector, so a
step read as a conveyor sliding sideways rather than a ring turning. Travel is
now per slot: each bubble starts at the position of the neighbour it is
replacing. Because the middle slot sits `ARC_DEPTH` below the outer two, a
bubble entering the middle arrives from higher up (`-10px`) while one entering
an outer slot arrives from lower down (`+10px`), and that height difference is
what reads as rotation around a circle. Slots 1 and 3 are the same height, so
they share one travel variant and only the middle needs its own — eight
keyframes (2 directions x 2 variants x 2 replay phases) rather than twelve.

The bubble arriving from off the ring now fades up as it travels, so a step
shows one option appearing while the one it displaced is gone. The three
animations are layered on three elements so none of them contend: the button
owns the arrival fade, the motion box owns the arc travel, and the core keeps
its idle float.

**Verified.** `shipped_language_popover_cycles_three_bubble_options_on_scroll`
asserts all three bubbles arm travel, that the middle slot's variant differs
from the outer two, that each class resolves to real keyframes through
`computed_style.animations`, and that exactly the trailing bubble carries the
arrival fade. Under `nix develop`, `cargo test -p mesh-core-shell` holds at 18
failures against the 20-failure in-flight baseline. Timing and arc feel are
still unconfirmed in a running compositor.

## 2026-07-30 — bubble popovers were unselectable: child-surface hit testing ignored buffer padding

area: shell input, promoted popovers, navigation-bar frontend

Hovering the language or theme bubbles dismissed the popover instead of
letting anything be picked. A promoted `<popover>` gets a buffer padded beyond
its own box so descendant blur and transform overshoot has pixels to paint
into, and `paint_child_surface` places the subtree at that padding offset —
for the shipped bubble popovers the padding measured `(50, 52, 50, 54)` around
a `132x60` content box, dominated by the `backdrop-filter` blur radius.
`handle_child_surface_input` offset the subtree to its own local origin and
ignored the padding, so every pointer coordinate arriving in padded buffer
space was skewed by roughly 50px. Hits landed outside the popover node, which
dispatched `pointerleave` on it, which started the 400ms close bridge.

`ShellComponent::handle_child_surface_input` now takes the same
`content_offset` as `child_surface_debug_tree` and `paint_child_surface`, and
both call sites pass the child's stored `content_padding`. Regressions:
`navigation_language_option_cancels_hover_close_and_accepts_mouse_click` and
`navigation_language_popover_closes_when_pointer_leaves_promoted_popup` now
drive padded coordinates and assert the padding is non-zero; both fail against
the old offset.

Two module-level dismissals were fixed alongside it. Focus leaving a bubble
scheduled a close even when the pointer was still inside the popover, so
clicking a second bubble shut it 400ms later; the blur handler now only closes
when the pointer has actually left. Scrolling the ring also kept it alive.

Bubble geometry and scrolling: `ARC_DEPTH` drops from 24px to 10px and the
horizontal step from 28px to 38px, so the three options read as a row with the
middle one slightly low — a hint of a circle, not a half-moon — instead of
overlapping discs. Stage height is derived from those constants rather than
hardcoded, moving the popover content box from `112x74` to `132x60`. Scrolling
now turns the ring: `BubbleOptions` gained a `rotation` prop whose
direction-plus-tick token selects one of four one-shot slide keyframes (two
alternating phases per direction so consecutive steps replay), the language
popover no longer re-centres its window on every render — which had reverted
each scroll step before it painted — and the theme selector rotates its three
bubbles in place.

The active mark also never moved to the picked bubble. Applying a theme is a
round trip through the shell: `onSelectTheme` published `shell.set-theme` and
then waited for `theme.current` to report back, so every render kept marking
the theme the user had just moved away from. Both popovers now hold an
optimistic selection — the value they asked for plus the value it replaced —
and release it once the service reports anything other than the replaced value,
which covers both the request landing and a change made elsewhere. Regressions:
`shipped_theme_selector_marks_the_picked_bubble_active_immediately` and
`shipped_language_popover_marks_the_picked_bubble_active_immediately`.

**Verified.** Under `nix develop`, `cargo test -p mesh-core-shell` goes from 20
to 18 failures with no new ones; the two remaining fixes are the rewritten
`shipped_language_popover_cycles_three_bubble_options_on_scroll`, which now
drives the real navigation surface and asserts the ring opens on `HI/EN/SK`,
steps to `EN/SK/DE`, and arms the rotation class. The pre-existing
`mesh-core-animation` build errors and the remaining 18 shell failures are
unchanged from the in-flight baseline.

## 2026-07-30 — live frontend catalogs publish atomically

area: shell, frontend composition, correctness

Every frontend surface used to receive an `Arc<FrontendCatalog>` at construction.
Live activation rebuilt that catalog only for a newly mounted top-level surface;
existing surfaces kept the old pointer, while activating a component or widget
returned before updating any host. Deactivation and hot reload had the same
split ownership in reverse: removing a widget did not recompose its slot hosts,
and source reload mutated only the reloading surface's private `Arc`.

`Shell` now owns one shared, versioned catalog handle. A complete candidate is
compiled before publication, then swapped as one generation and adopted by
every component. A failed surface mount restores the prior generation before
any existing host is notified. Component/widget activation and deactivation
publish even when no surface is added or removed, and hot reload updates the
same handle before the shell rebinds sibling hosts.

Invalidation follows the reverse composition graph across explicit component
imports and hosted slots. Unaffected surfaces merely adopt the new snapshot.
Affected surfaces discard retained composition state and memos, but remove only
Lua runtimes and prepared local styles belonging to modules that actually
changed; the root and unrelated embedded runtime state survive. Slot
contributions are now indexed only for enabled installed modules, so toggling a
widget changes its hosts without making disabled component code unavailable to
declared imports.

The regression paints a live slot contribution, publishes a generation without
it, proves the surface holds its coherent old snapshot until notification, then
checks that the root runtime generation is unchanged, the widget runtime is
gone, and the next tree contains no stale slot content. The shipped live
frontend activation/deactivation slice passes 2/2. `cargo check
-p mesh-core-shell` passes under `nix develop`; the full shell suite reports 570
passed / 18 failed / 122 ignored, exactly the existing 18-failure baseline by
name.

## 2026-07-30 — component host globals isolated in the shared Luau realm

area: scripting runtime, correctness

Frontend components deliberately share one thread-local Luau realm, with a
separate `_ENV` per component as the isolation boundary. One host-seeding path
violated that boundary: `ScriptContext::set_global_state` wrote module-specific
values to `lua.globals()`, and `create_runtime_for_component` used it for
`this`. Creating another module therefore replaced the descriptor that an
already-live module resolved later from either a template expression or a Lua
handler.

The API is now `seed_context_global`: it writes directly into the owning
component's `_ENV`, registers the key as host-owned so reactive-global discovery
does not absorb it, and keeps the Rust-side state mirror intact. Shared Luau
globals are no longer used for component descriptors. The audit found no other
callers of the old API; the remaining realm-global writes are the deliberate
canonical service-payload and locale caches shared by all authorized proxies.

The regression creates two module contexts on one `SurfaceVm`, installs
different `this.package.id` values, then evaluates both templates and calls both
handlers after the second context exists. Before the fix, the first template
read `@mesh/second`; after the fix all four reads retain their owning module.

**Verified.** Under `nix develop`, `mesh-core-scripting` reports 179 passed / 27
ignored. The focused shell manifest-descriptor slice passes 2/2. The full shell
suite reports 569 passed / 18 failed / 122 ignored, exactly the documented
baseline with the same 18 failures by name.

## 2026-07-30 — settings values are validated, and say so

area: configuration

The single store (below) read every value with `.and_then(parse_x)`, so a wrong
type, a bad enum value, or a misspelled key produced `None` and the field kept
its default *in silence*. Unknown keys were never enumerated at all. For a file
whose whole purpose is hand-editing, that is the worst failure mode: three ways
to change nothing and hear nothing —

```json
"@mesh/navigation-bar": { "surface": { "anchr": "bottom" } },   // typo'd key
"@mesh/quick-settings": { "surface": { "anchor": "botom" } },   // bad enum
"shell": { "tooltip": { "delay_ms": "300" } }                   // wrong type
```

`docs/spec/08-settings.md` §1 already required the behavior ("rejected with a
diagnostic and the stored value is ignored"). The ignoring half worked; the
diagnostic half did not exist. All three now report namespace, key path, the
value found, and what to do, and the shell still starts on declared defaults.

**Shape.** `SettingsDiagnostic { severity, namespace, key_path, message,
suggested_action }` in `mesh-core-config`, modeled on
`ModuleManifestDiagnostic` — the `suggested_action` pairing is what makes the
manifest diagnostics actionable, and a hand-edited file needs the same. The
walk is a declarative schema (`FieldSpec` / `FieldKind`) so one implementation
serves both namespaces: `SHELL_SETTINGS_FIELDS` sits next to `ShellSettings`,
whose serde defaults define what a rejected value falls back to, and
`SURFACE_FIELDS` sits in `mesh-core-surface-config`, which owns the placement
vocabulary.

**Enum fields carry their parser, not a copy of its strings.**
`FieldKind::Enum { accepts, values }` takes `accepts: fn(&str) -> bool` — the
actual `parse_surface_edge`/`parse_keyboard_mode`/etc. — so aliases those
parsers accept (`"toplevel"`, `"csd"`, `"on-demand"`) are not reported as
errors, which a duplicated string list would have gotten wrong. `values` is the
canonical list quoted back in the suggestion, built from the `*_name` functions
(now `const fn`); `*_is_listed` guards make adding an enum variant a compile
error until its value list is updated. A test asserts every listed value
parses, so the advice a diagnostic gives always works.

**Severity.** Wrong type and bad enum are errors. An unknown key is an error
only when a known key is within typo distance (`anchr` → `did you mean
"anchor"?`, Levenshtein with a length-scaled budget so `top` is not "corrected"
to `left`); with no near match it is a warning, because it may be a
forward-looking key or one owned by a reader this walk does not know about.
Role-inert fields (`resizable` on a `role: "layer"` surface) warn rather than
error, and `promotable` surfaces are exempt entirely — they legitimately carry
both roles' fields, so anything stricter cries wolf on shipped `@mesh/settings`.

**Nothing is fatal.** `resolve_shell_settings` is now infallible: values are
checked *before* the merge, so what reaches serde is already well-typed. Before
this, `"delay_ms": "300"` failed `serde_json::from_value` and lost the whole
namespace. `set_namespace`/`merge_namespace`/`reset_namespace` dropped their
`Result` — they can no longer fail.

**Surfacing.** `resolve_frontend_module_settings` returns diagnostics rather
than logging: only the caller knows whether it is reading the store at startup
or re-reading it after a save. Live reload reports only what is new
(`new_settings_diagnostics`), so a user fixing one of five mistakes sees four,
not five again. New `mesh-shell config doctor` runs the same validation without
starting a shell — errors first, exit 1 on any error, and it also reports
orphaned namespaces (a module that is no longer installed), which closes that
separate backlog item. Against the repo's own `config/settings.json`: `no
problems found`, exit 0, asserted by a unit test as well.

**Out of scope, deliberately.** `props.*` values pass through unvalidated —
their declaration is the `<props>` block, which does not exist yet
(`docs/spec/03-components.md`); `MODULE_NAMESPACE_FIELDS` marks them `Opaque`
and the backlog carries the follow-up. The `mesh.settings` service contract
remains its own item.

Tests: 13 new in `mesh-core-config`, 12 in `mesh-core-surface-config` (bad
enum, wrong type, unknown key with and without a near match, role-inert
warning, promotable exemption, alias acceptance, clean namespace), plus a
`mesh-core-shell` guard that every accepted `tooltip.position` resolves to a
real anchor. Shell suite: 569 passed / 18 failed / 122 ignored — the same 18
failures by name as the 568/18/122 baseline, plus the new tooltip test.

`mesh-core-surface-config` now depends on `mesh-core-config`
(`docs/crate-boundaries.md` updated) for the diagnostic type and the schema
walk.

## 2026-07-30 — one settings store

area: configuration

Settings lived in four places: `config/settings-default.json` (bundled
defaults), `config/shell-settings.json` (user shell overrides), a
`config/settings.json` inside each module directory (user surface/prop
overrides written into shipped module source), and `ShellSettings.modules` for
per-module icon overrides. All four collapse into one
`config/settings.json` — `$MESH_HOME/settings.json` outside a checkout,
`MESH_SETTINGS_PATH` overriding both — keyed by namespace exactly as
`docs/spec/08-settings.md` §1 specified: `shell` for core preferences, module
ids and interface ids for everything else.

The store is **sparse**. Declared defaults live in `ShellSettings`'s serde
defaults and in each module's `mesh.surface` block; nothing copies them into
the file. `mesh-shell config eject <module-id>` materializes a module's
effective surface placement into its namespace for hand-editing, which is the
discoverability the sparse model otherwise gives up. `config path`, `config
show [namespace]`, and `config reset <namespace>` round it out.

Three things fell out of the consolidation rather than being separate work:

- **The old shell merge was lossy.** `merge_shell_settings` replaced whole
  sections, so a user file mentioning only `theme` reset tooltip and keyboard
  to whatever the defaults file said. Merging is now recursive per key; arrays
  still replace wholesale, since a pack chain or activation-key list is a
  complete ordered replacement by intent.
- **Two watchers watched one file.** `settings_watch` (shell settings) and the
  per-component `module_settings_path` poll now target the same path, so the
  per-component poll is gone: the shell reloads the store once and pushes it to
  every component through `ShellComponent::apply_settings`.
- **Keyboard input no longer touches the filesystem.** `current_keyboard_settings`
  ran two `std::fs::metadata` calls plus an mtime-keyed cache on every key press
  and release; it now reads `self.settings.shell().keyboard` off the shared
  store. This closes the backlog item "Remove filesystem metadata calls from
  keyboard events" — the fix was structural, not a new cache, so the mtime cache
  and its release microbenchmark are deleted rather than retuned.

`@mesh/navigation-bar` was storing `keyboard_mode: "on_demand"` against a
manifest declaring `"none"`. A surface that declares a `mute` keybind needs
keyboard focus by design, so that moved into the manifest as the author default
it always effectively was, rather than surviving as a user override. Its
genuine override (`i18n.default_locale: "sk"`) is the one module entry in the
new file. The other three modules' stored files held only `{"props":{"global":{}}}`
and are simply gone.

Backend provider props now read from the provider module's namespace instead of
`ShellConfig.modules` (TOML `config.toml`), which nothing populated.

**Measured.** `mesh-core-config` 20 passed; `mesh-core-surface-config` 14
passed, including round-trip proofs that an ejected block re-resolves to the
layout it was ejected from, for both layer and window roles. Shell suite: 568
passed / 18 failed / 122 ignored, against the 556/18 baseline recorded
2026-07-28 — same 18 failures, 12 additional tests passing. The whole-workspace
run is otherwise green except two pre-existing failures outside this change

## 2026-07-30 — runtime promotion between widget and window

area: presentation, shell, module system, styling

Phase 4 of
[`../todos/pending/2026-07-28-toplevel-window-surfaces.md`](../todos/pending/2026-07-28-toplevel-window-surfaces.md).
A live surface can now be moved between `zwlr_layer_surface_v1` and
`xdg_toplevel` without losing component state. `@mesh/settings` demonstrates it:
it opens as chrome anchored to the right edge with a "pop out" control, and once
popped out the same header shows "dock back" instead.

**The presentation layer already did the hard part.** `configure` has destroyed
and recreated the compositor object on a role change since phase 1, and the
render loop's `config_changed` already compared `last.role`. What was missing was
purely shell-side: a trigger, and dropping the cached state that describes the
object that was just destroyed. `set_surface_role` clears
`last_surface_config` and `known_surface_size` and forces a full present —
without the first, the render loop compares against the old config and never
sends the configure that creates the replacement; without the second,
`resolve_dynamic_surface_size` short-circuits on a size measured under the other
role, which is exactly wrong given the two roles size in opposite directions.

**`promotable` is a new manifest field, and it had to be.** The role-mismatch
diagnostic from phase 1 rejects layer fields on a window and vice versa, which is
right for a static role and wrong for a surface that holds both over its life —
settings needs `anchor` for its docked form and `title`/`appId` for its window
form. `"promotable": true` is the single exemption from that diagnostic, and it
doubles as the opt-in gate: a role change is refused for a surface that does not
declare it, because a root laid out as a 32px panel widget is not automatically a
sensible window. A test asserts both halves — the same manifest without the flag
is still a contradiction.

**The role is CSS state, not script state.** `:windowed` joins the four
compositor states as a fifth ambient pseudo-state (bit `1 << 17`). Settings ships
both header controls and lets `display: none` decide which exists, so the chrome
follows the surface's real role even when the role changed from outside the
component — a settings override or a compositor keybind over IPC. A component
tracking the role in a Lua variable would disagree with reality the moment that
happened. `display: none` rather than a visual hide so the inactive control is
out of layout and not clickable.

Three things worth knowing for the next surface that does this:

- **The old compositor object must be destroyed eagerly, not by `configure`.**
  This is the one real bug in the change, and only a live compositor found it.
  `configure` does swap the object on a role change, but it runs *partway through*
  the render frame — after the loop has already read `window_configured_size` and
  laid content out against it. Demotion therefore measured against the outgoing
  window's size, found its measurement already agreed with that, skipped the
  corrective configure, and left the new layer surface stranded at the 1×1 that
  the layer-shell backend clamps an unmeasured 0×0 request to. Every layer
  surface's first show sends 0×0 and relies on a second, corrected configure once
  `paint` has built the tree; a role change has to enter that same path.
  `set_surface_role` now calls `destroy_surface` itself, so
  `window_configured_size` reports `None` from that point on. Regression test
  asserts the destroy happens.
- **`observe_window_states` does not invalidate the surface config.** It
  invalidates STYLE|LAYOUT|PAINT|METRICS, so `surface_role_changed` has to add
  SURFACE_CONFIG explicitly or `render` skips `render_layout` and the
  presentation layer is never asked to swap anything.
- **The window-states projection stays keyed off the shell-surface record**, not
  the component's requested role. An earlier attempt keyed it off the component
  so a freshly promoted window would not wait a frame; that broke
  `compositor_window_states_reach_the_component_each_render` and was unnecessary
  anyway — `render_layout` updates the record the same frame, and demotion needs
  no delivery at all because `surface_role_changed` clears the states itself.

Triggers: `shell.set-surface-role` / `shell.toggle-surface-role` on the script
event channel, and `shell:promote_surface:` / `shell:demote_surface:` /
`shell:toggle_surface_role:` on the IPC line protocol. The IPC path exists
because MESH keybinds are focused-surface actions and cannot grab a global
hotkey, so a compositor binding has to shell out.

Also refused, with a diagnostic rather than silently: promoting a surface
realized as a popover (it has no independent placement, and its trigger would
point at a destroyed surface), and promoting when the compositor has no
`xdg_wm_base`. The latter is checked *before* teardown, because window creation
fails inside `configure` — after the old layer surface is gone — which would
leave the surface unmapped with no way back.

Settings' first configure is now the layer shape again (920×900: the 700px
measured root plus the 200px tooltip overlay reserve) rather than the window
shape (920×700, no reserve); `frontend_module_activation_mounts_shipped_surface_live`
was updated to match.

**Verified against live Hyprland.** Driven over IPC across
show → promote → demote → promote, with `hyprctl` as the independent check. The
configure sequence per role change is `0×0` then the corrected size, and the
sizes come out exactly as designed:

| State | Configure | `hyprctl` |
| --- | --- | --- |
| shown as chrome | 0×0 → 920×900 | `LAYER @mesh/settings 920x900` |
| promoted | 0×0 → 920×700 | `TOPLEVEL class='mesh.settings' title='Settings' size=[1429,841]` |
| demoted | 0×0 → 920×900 | `LAYER @mesh/settings 920x900` |

920×900 is the layer shape (700 measured + 200 tooltip reserve) and 920×700 the
window shape (no reserve), which is the distinction phase 1 introduced. The
promoted toplevel is tiled by Hyprland into 1429×841 — the compositor overriding
the requested size is the whole point of the sizing inversion, and the content
absorbs it through the `:tiled` rule. `app_id` and the localized title both land.
The transient `layer surface configured 0x0 … clamping to 1x1` ERROR on each
change is the pre-existing first-configure noise every layer surface logs (
`@mesh/touch-gesture-proof` does the same on show), corrected by the retry in the
same frame.

Shell suite: 566 passing, 18 failing, 123 ignored under `nix develop`. The 18 are
the same set as the 2026-07-28 baseline — verified by diffing the failure lists
with and without this change. Pre-existing and untouched: one
`mesh-core-elements` failure, two `mesh-core-module` failures, and three
`mesh-core-animation` *test-compile* errors.

**Left open.** Phase 5, per-widget promotion — promoting a widget embedded in
another surface, rather than a whole surface — still depends on the shared
surface VM and on multi-instance frontend modules. The typed `surface.*`
automation envelope and the `mesh surface toggle-role` CLI subcommand land with
the rest of spec 11; only the raw line protocol is wired today.

## 2026-07-29 — window states as CSS state

area: presentation, styling

The compositor's `xdg_toplevel` states arrived on every configure and were
logged and dropped, so a window could not tell fullscreen from floating. They
are now `WindowStates` on the presentation role, delivered to the component
through `ShellComponent::surface_window_states_changed`, and projected onto the
tree as four pseudo-states: `:fullscreen`, `:maximized`, `:activated`,
`:tiled`.

**They are carried on every node, not just the root.** The selector subset has
no descendant combinators, so a state that lived only on the surface root would
be unreachable from the elements that need it — a sidebar cannot write
`.window:fullscreen .sidebar`. Projection happens in
`annotate_runtime_tree_inner`, which already writes every node's
`ElementState`, so the cost is four bools per node and no extra traversal. The
four new state bits ride the existing `StyleRuleIndex` bit index, so candidate
lookup and matching needed no special case; the diagnostic tree fingerprint's
`state_bits` widened from `u16` to `u32` to fit them.

**Delivery sits ahead of the `wants_render` gate** in `render_components`. A
compositor state change is exactly what makes an otherwise-quiet window want to
render; asking behind the gate strands a fullscreened surface at its floating
style until something else dirties it. `observe_window_states` invalidates the
way a resize does (STYLE|LAYOUT|PAINT|METRICS, cached measurement cleared)
rather than taking the targeted interaction-restyle path — the change is
ambient and happens at human frequency.

`@mesh/settings` uses it: the floating 920×700 stays on the base rule, and
`:fullscreen`/`:maximized`/`:tiled` take `width: 100%` and clear the floating
minimum. Its `"resizable": false` is gone — pinning min to max is what stopped
the compositor resizing it in the first place, which is why a fullscreened
settings window was still a 920×700 island.

**Left open.** `min-*`/`max-*` are `Option<f32>` while `width`/`height` are
`Dimension`, so `max-width: 100%` cannot clamp a fixed root to its surface and
each filling rule must clear the floating minimum by hand. Backlog item filed
under *Tech debt*.

**Measured.** `mesh-core-shell --lib` 560 passed / 18 failed against a
stash-verified 556 / 18 baseline — the same 18 failures by name, plus the 2 new
tests and 2 real-surface tests that the settings CSS change fixed. Rest of the
workspace matches its baseline: the pre-existing failures in
`mesh-core-elements` (1), `mesh-core-frontend` (1), and `mesh-core-module` (2)
are unchanged, and `mesh-core-animation`'s test target still does not build.

## 2026-07-29 — toplevel window surfaces

area: presentation

`mesh.surface.role: "window"` realizes a frontend module as an `xdg_toplevel`
instead of layer-shell chrome. `@mesh/settings` ships as a window; panels,
launchers, and popovers are unchanged.

The role axis already existed in the presentation layer — the internal
`SurfaceRole` enum (renamed `WaylandRole`) gained a `Window` variant alongside
`Layer` and `Popup`, so the whole SHM / present / scale / damage / input path is
shared. `LayerSurfaceConfig` became `SurfaceConfig` and `LayerShellBackend`
became `WaylandSurfaceBackend`, since neither is layer-specific any more.
`XdgShell` was already bound for popup positioners; it now also drives
`create_window`, a real `WindowHandler`, and per-toplevel decoration objects.
The comment at `handlers.rs` claiming MESH never creates toplevels is gone.

**Sizing inverts, and that is the whole design.** A layer surface tells the
compositor its CSS-measured size; a window is *told* its size by the configure
and lays content out into it. `window_configured_size()` overrides the measured
size once the compositor has named one. The measured size is only the initial
request, so a resizable window deliberately publishes **no** min size —
publishing the natural size as a minimum would let a user grow a window but
never shrink it. `resizable: false` pins by reporting the content size as both
min and max.

**Three things only showed up against a live compositor** (Hyprland 0.56):

1. The tooltip overlay reserve leaked into the toplevel's pinned size — a
   920×700 settings root mapped as a 920×900 window. Windows now take no
   reserve: a toplevel's size *is* its content size, and a tooltip that must
   escape a window is an `xdg_popup`, which `<popover>` already promotes to.
2. Hiding by detaching a buffer unmaps a toplevel, and remapping needs a fresh
   configure the compositor is under no obligation to send for a commit
   carrying no new state. A re-shown window waited out the 500ms configure
   deadline every frame and never reappeared. Windows are now destroyed on hide
   and recreated on show — the lifecycle promoted popovers already use.
3. `destroy_surface` silently ignored anything that was not a layer surface, so
   fix 2 was a no-op until it was widened to all non-popup roles. Symptom: hide
   left the window mapped.

Also: layer placement fields on a window (and window fields on a layer surface)
are a `surface_role_field_mismatch` graph diagnostic rather than a silently
dropped key; `keyboard_mode` is skipped for windows, which also protects them
from the synthetic 1×1 hidden geometry; popups can be parented to a window
(`xdg_surface.get_popup`) as well as a layer surface; the user can move a
surface between roles through the sparse settings store.

**Measured.** Workspace suite 1640 passed / 22 failed, against a
stash-verified pre-change baseline of 1630 / 22 — the same 22 failures by name,
so no regressions; 10 new tests. Clippy warning count unchanged at 248.
`frontend_module_activation_mounts_shipped_surface_live` asserted the settings
surface configured at 920×900 and now asserts 920×700: that test encoded the
layer-surface geometry, and the reserve removal above is the intended change.
Note `mesh-core-render`'s lib tests are flaky under the workspace run — one
sampled run failed 8 of them and two adjacent runs failed none, in a crate this
work does not touch.
`mesh-core-animation` does not compile its test target on this tree (unrelated
pre-existing errors in `keyframes.rs` / `transition.rs`) and was excluded from
both runs. Live on Hyprland 0.56: window maps at exactly 920×700 with title
`Settings` and app id `mesh.settings`, and three hide/show cycles over the IPC
socket each destroyed and recreated it at the same size.

**Left open.** Runtime promotion between widget and window, the
`surface.promote` / `surface.demote` IPC verbs, and window states
(maximized/fullscreen/tiled) as CSS state on the root — all three are in
`docs/BACKLOG.md`. The compositor delivering `xdg_toplevel.close` was not

## 2026-07-31 — LSP serves `settings.json` from the runtime's own schema

area: mesh-tools-lsp, settings

`config/settings.json` was the one MESH-owned JSON file the editor knew nothing
about: no completion for namespaces or keys, no idea which themes, locales, or
icon packs exist, and no diagnostics until the shell was started and its
validation ran.

The manifest support already had the pieces (a schema tree driving completion,
hover, and diagnostics; a tolerant cursor scanner for mid-edit JSON), so those
moved out of `manifest/` into a document-agnostic `json/` module. `manifest/`
now supplies its hand-written tree; the new `settings/` module supplies one it
*derives* rather than restates — `mesh_core_config::SHELL_SETTINGS_FIELDS` for
the `shell` namespace and `mesh_core_surface_config::MODULE_NAMESPACE_FIELDS`
for module namespaces. A key the store stops accepting stops being completed,
with no second copy of the schema to keep in sync. What the LSP adds is prose
(a `FieldKind` carries no documentation) and the values discovered on the
machine.

Discovery, added to `ModuleRegistry`: themes from the theme directory and the
workspace's `config/themes` plus theme modules; locales from every
`config/i18n/*.json` a module ships and the default locales modules declare;
icon packs, and every installed module and interface id, from the manifests
already scanned. These are offered but never enforced — a theme or pack can
live outside the scanned workspace, so refusing it would be worse than not
suggesting it. Enum values (`tooltip.position`, `surface.anchor`,
`surface.layer`, `keyboard_mode`, …) come from the runtime parsers and *are*
enforced, as they already were at load time.

Two shapes the manifest schema could not express were added to the tree: an
open object (known keys beside arbitrary namespace keys, so an uninstalled
module's namespace is described rather than flagged — spec 08 §7 keeps it) and
a runtime-discovered suggestion list.

Hover also stopped requiring the cursor to sit at the end of a key: the cursor
context now carries the whole string literal, not just the prefix before the
cursor, so hovering the middle of `"anchor"` documents `anchor`. That bug was
in the manifest hover too, and is fixed for both.

`cargo test -p mesh-tools-lsp` passes 81 unit + 1 manifest + 5 settings
integration tests. The integration tests run against the real workspace: the
shipped `config/settings.json` validates with zero diagnostics, and discovery
must actually find `gruvbox-dark`, `en`/`sk`, `@mesh/icons-material-symbols`,
and `@mesh/navigation-bar` — so the guards fail if discovery silently stops
finding anything rather than passing on an empty list.

## 2026-07-31 — `min-`/`max-` size constraints take full dimensions

area: mesh-core-elements (style, layout), mesh-core-animation, mesh-tools-lsp

`width` and `height` had been `Dimension` (length, percentage, `auto`,
`fit-content`) for a long time, but `min-width`, `max-width`, `min-height`, and
`max-height` were still `Option<f32>` on `ComputedStyle`, parsed through
`resolve_number_with_variables`. Anything that was not a bare length silently
became a length: `max-width: 100%` resolved to `parse_px("100%")` → `Some(0.0)`,
and so did `max-width: none`. A percentage clamp was not merely unsupported, it
collapsed the element.

All four are now `Dimension`, resolved with the same `parse_dimension` path as
`width`/`height` through a thin `parse_size_constraint` wrapper that maps the
CSS keyword `none` to `Dimension::Auto` — `none` and `auto` both mean "no
constraint", which is what `Auto` already means to Taffy's `min_size`/`max_size`.
`layout.rs` maps them with the existing `taffy_dimension`, so percentages
resolve against the parent's inner size the way `width` does.

Two follow-on changes fell out of the type change:

- The four properties joined the typed-literal pre-lowering fast path in
  `typed_literal_value`/`apply_typed_literal`, which previously handled only
  `width`/`height`/`flex-basis` among the dimension-valued properties. Static
  `min-`/`max-` literals now lower once instead of re-parsing per node.
- `AnimatableStyle` carries them as `Dimension` and interpolates them with the
  existing `lerp_dimension` instead of `lerp_option_f32`, so a transitioned
  `max-width` animates in whatever unit it was authored in.

The retained-tree style fingerprint switched from `hash_option_f32` to
`hash_dimension` for the four fields, so a percentage change is a real style
change rather than a hash collision against the length that happened to parse
out of it.

Shell-owned constraints (`collapse_promoted_popover_wrappers`,
`constrain_error_placeholders`) now write `Dimension::Px` values; behavior is
unchanged.

Docs: `docs/spec/04-styling.md` §6 previously told authors that percentages were
unavailable and that a floating minimum had to be cleared per state; it now
documents the accepted value set. `docs/css-coverage.md` gained the same detail,
and the LSP's CSS knowledge base offers `auto` / `none` / `100%` as completions
for all four.

Regressions (`mesh-core-elements`):
`percentage_max_width_clamps_a_fixed_root_to_its_container` (920×700 root capped
to a 400×300 container), `percentage_min_and_max_constrain_children_against_the_parent`
(`max-width: 25%` and `min-width: 50%` of a 400px row), and
`auto_max_width_leaves_the_element_unconstrained` — the last one is the guard
against the `none`/`auto` → zero-clamp failure mode. `size_constraints_accept_every_dimension_form`
covers resolution for lengths, percentages, `auto`, `none`, `fit-content`, local
variables, and theme tokens.

Suites: `mesh-core-elements` 205 passing / 2 failing, `mesh-core-shell --lib`
582 passing / 18 failing / 122 ignored, `mesh-core-frontend --lib` 62 / 1.
Every one of those failures was verified pre-existing by stashing the change and
re-running — the shell's 18 are the same 18 by name as the recorded baseline.

Incidental: `mesh-core-animation`'s test module did not compile (a test helper
was missing `AnimatableStyle::visibility`, and another wrote the removed

## 2026-07-31 — Child→parent `bind:this` event push reaches the parent's template

area: mesh-core-scripting, mesh-core-shell

`resync_binding_neighbors` documented both directions of a live `bind:this`
link, but only one of them worked. Both are gated on the neighbour's
`live_binding_external_accessed` flag, and that flag was set in exactly two
places, both inside the proxy the *parent* holds: the function wrapper in
`__index` and the `__newindex` write. Both set the **child's** flag.

So parent→child was covered — `child.set_value(99)` flags the child, the child
resyncs, its template re-renders. Child→parent was not. A parent subscribing
with `child.Changed:on(fn)` got the child's real channel table handed straight
back, with no wrapper anywhere; when the child later ran `self.Changed:fire(7)`,
the parent's closure ran and mutated the parent's `_ENV`, but nothing flagged
the parent, so `resync_binding_neighbors` skipped it and the new value never
reached the parent's reactive state. The documented feature was unusable.

The channel branch of `__index` now returns a per-parent wrapper table
(`parent_subscription_channel`) instead of the raw channel. The wrapper
delegates everything to the real channel through its metatable — `fire`,
`emit`, and `__subscribers` are shared, so both sides still see one subscriber
list — and overrides `on`/`subscribe` to wrap the registered callback in a
function that sets the **parent's** flag before invoking it. That is the mirror
image of the existing `__index` function wrapper, and it keeps the same
precision: the flag is set when a callback actually runs, not when the parent
reads the channel or subscribes, so an untouched parent is still skipped by the
resync. Wrappers are memoized per event name.

Regression: `child_self_event_fire_resyncs_the_parent_that_subscribed` — the
parent subscribes from a handler, the child fires from its own handler, and the
parent's reactive `received` must become the fired value. It fails on the old
code with `Some(-1)` against `Some(7)`. The same test asserts the parent is
*not* flagged by subscribing, which is what keeps the neighbour skip
meaningful.

Suites: `mesh-core-scripting` 179 passing / 27 ignored (unchanged).
`mesh-core-shell --lib` 583 passing / 18 failing / 122 ignored — the same 18
failures by name as the standing baseline, with the new test passing.

Not done here: the shipped navigation language and theme triggers still
re-derive popover state in their `render()` hooks, which is the workaround this
bug forced. Removing the pull is now possible but changes live popover
behaviour, so it is a separate backlog line needing Hyprland verification.

## 2026-07-31 — Module script scanning uses a real Luau parser

area: mesh-core-module

Graph scanning cross-checks module scripts against module declarations:
translation keys against the default catalog, published channels against the
shell-owned event namespace, backend events against the interface contract.
Three of those checks were substring searches over the raw file text, and they
were wrong in both directions.

`content.find("t(")` matches the tail of any identifier, so every `t(` inside
`format(`, `assert(`, `insert(` counted as a translation-key call and its first
string argument was reported as an undeclared key. On the shipped tree,
`string.format("%d%%", safe)` in `navigation-bar/src/components/volume-button.mesh`
was reported as the key `%d%%`. Confirmed directly before the change:

```
extract_t_keys_from_mesh_source(<script with format/assert/t>)
→ ["%d%%", "boom", "nav.volume"]
```

The searches also read comments, string literals, and `<style>` blocks as if
they were code. The `!key.contains(' ')` and `!key.contains('{')` filters in
each scanner were band-aids over exactly this — `"%.1f GB"` was suppressed only
because it happens to contain a space.

`full_moon` 2.2.0 with its `luau` feature is now a dependency of
`mesh-core-module`, and `package/luau_scan.rs` walks a real AST. A callee is
matched as a whole dotted path (`t`, `mesh.events.publish`,
`mesh.service.emit_event`) built from the call's prefix and leading `.` field
accesses, so `insert(` no longer resolves to `t`. Only a first argument that is
a string literal is reported; a dynamic call site contributes nothing, which is
the same "not statically checkable" answer as before. The space/brace filters
are gone — they have nothing left to suppress.

For a `.mesh` file, both halves run Luau, so both are scanned: the `<script>`
chunk and every template expression (interpolations, `@if` conditions, `@for`
iterables, `{...}` attribute bindings, pre-bound handler-call arguments). A
template expression is parsed as the operand of a `return`, which is how it is
evaluated. Backend `.luau` files are plain chunks.

Two constraints shaped the implementation:

- **`full_moon` needs a large stack.** It is recursive descent, and its
  unoptimized frames are big enough that a ~1000-line module script overflows
  the 2 MiB a default debug thread gets — which aborts the process rather than
  failing the scan. Parsing runs on a worker thread with a 16 MiB stack. Stack
  use tracks expression nesting, not file length: eight concatenated copies of
  the largest shipped script (7,856 lines) parse inside 8 MiB, and there is a
  regression pinning that.
- **One parse per file, not one per check.** The visitor collects every
  requested callee in a single walk, and the graph loop precomputes all files'
  results with `par_iter` before running the (still serial, still
  deterministic) diagnostic loop.

Cost, release, 38 shipped `.mesh` files / 7,877 lines, three runs: serial
45.6–81.0ms, parallel 19.7–35.3ms (2.3–2.6x). That is a real addition to graph
load — the substring scan was effectively free. It is the price of the checks
being correct, but these are authoring diagnostics and do not belong on the
path to first paint; moving them to `mesh-shell config doctor` and a dev flag
is now a backlog item, as is parsing each file once instead of three times
(the icon and keybind extractors each call `parse_component` again).

Tests: 8 unit tests in `luau_scan` covering whole-identifier matching, comments
and string literals, dotted paths, dynamic arguments, bracket and
parenthesis-free string calls, multi-callee single-parse, unparseable input,
and the stack ceiling. Plus `shipped_frontend_translation_keys_are_declared`,
which asserts every key the scanner reports across every shipped frontend
module exists in that module's own catalog — the end-to-end guard that would
have failed on `%d%%` before.

Three test fixtures were bare markup fragments (`<text>{t('x')}</text>`) rather
than components, and one used nested double quotes inside a double-quoted
attribute. The AST path needs a parseable component, exactly as the existing
icon and keybind extractors already did, so those fixtures became real
components. Assertions are unchanged.

Suites: `mesh-core-module` 150 passing / 2 failing / 3 ignored — the two
failures (`navigation_bar_declares_icon_pack_dependency`,
`shipped_module_graph_loads_repo_module_fixture`) were verified pre-existing by
stashing the change. `mesh-core-shell --lib` unchanged at 583 / 18 / 122.

Note on licensing: `full_moon` is MPL-2.0 against this project's MIT. MPL is
file-level copyleft and linking is permitted; the dependency's own files stay
under MPL.

## 2026-07-31 — profile-owned composition and kind-aware local install

area: module graph, settings, installation, CLI, architecture

Implemented the first executable shell-profile slice behind an opt-in migration
boundary. `config/active-profile` selects `config/profiles/<id>.json`; without
that pointer the existing `config/module.json` decisions remain unchanged. A
profile stores positive root instances, explicit background services/provider
bindings/resource modules, and sparse per-instance surface overrides. Graph
loading derives the active closure from those seeds plus declared module and
resource dependencies, interface modules, provider base modules, and a sole
compatible provider. Unselected installed modules remain catalog nodes but do
not contribute to runtime topology.

Added `mesh-shell profile list/create/use/show/add/enable/disable/remove` and a
local-path `mesh-shell install`. Installation validates the canonical manifest,
requires explicit flags for elevated/high capabilities, copies into the graph's
configured modules directory, validates discovery and the candidate activation
closure, and removes the staged destination on failure. Direct frontend installs
create/re-enable `<module>#default`; other kinds remain available according to
their dependency/provider/resource semantics. Defaults are not copied: the
profile instance inherits manifest surface placement and future props until a
user writes an override. Live settings toggles now persist frontend/background
activation to the active profile and retain atomic rollback; legacy root-graph
writes remain the fallback.

Verification: `cargo check -p mesh-tools-cli`; 6/6 focused shell module-config
tests; 3/3 profile tests; CLI `profile list` and help smoke tests; `git diff
--check`. The complete 158-test `mesh-core-module` run reached 153 passed, 3
ignored, and 2 failures caused by pre-existing in-flight workspace changes:
navigation-bar no longer declares the icon-pack dependency expected by
`navigation_bar_declares_icon_pack_dependency`, and the locally added fifth
disabled proof module changes `shipped_module_graph_loads_repo_module_fixture`'s
expected count from four to five. Neither failing assertion exercises profiles
or installation.
