## 2026-07-30 — live frontend catalogs publish atomically

area: shell, frontend composition, correctness

Every frontend surface used to receive an `Arc<FrontendCatalog>` at construction.
Live activation rebuilt that catalog only for a newly mounted top-level surface;
existing surfaces kept the old pointer, while activating a component or widget
returned before updating any host. Deactivation and hot reload had the same
split ownership in reverse: removing a widget did not recompose its slot hosts,
and source reload mutated only the reloading surface's private `Arc`.

`Shell` now owns one shared, versioned catalog handle. A complete candidate is
compiled before publication, then swapped as one generation and adopted by
every component. A failed surface mount restores the prior generation before
any existing host is notified. Component/widget activation and deactivation
publish even when no surface is added or removed, and hot reload updates the
same handle before the shell rebinds sibling hosts.

Invalidation follows the reverse composition graph across explicit component
imports and hosted slots. Unaffected surfaces merely adopt the new snapshot.
Affected surfaces discard retained composition state and memos, but remove only
Lua runtimes and prepared local styles belonging to modules that actually
changed; the root and unrelated embedded runtime state survive. Slot
contributions are now indexed only for enabled installed modules, so toggling a
widget changes its hosts without making disabled component code unavailable to
declared imports.

The regression paints a live slot contribution, publishes a generation without
it, proves the surface holds its coherent old snapshot until notification, then
checks that the root runtime generation is unchanged, the widget runtime is
gone, and the next tree contains no stale slot content. The shipped live
frontend activation/deactivation slice passes 2/2. `cargo check
-p mesh-core-shell` passes under `nix develop`; the full shell suite reports 570
passed / 18 failed / 122 ignored, exactly the existing 18-failure baseline by
name.

## 2026-07-30 — component host globals isolated in the shared Luau realm

area: scripting runtime, correctness

Frontend components deliberately share one thread-local Luau realm, with a
separate `_ENV` per component as the isolation boundary. One host-seeding path
violated that boundary: `ScriptContext::set_global_state` wrote module-specific
values to `lua.globals()`, and `create_runtime_for_component` used it for
`this`. Creating another module therefore replaced the descriptor that an
already-live module resolved later from either a template expression or a Lua
handler.

The API is now `seed_context_global`: it writes directly into the owning
component's `_ENV`, registers the key as host-owned so reactive-global discovery
does not absorb it, and keeps the Rust-side state mirror intact. Shared Luau
globals are no longer used for component descriptors. The audit found no other
callers of the old API; the remaining realm-global writes are the deliberate
canonical service-payload and locale caches shared by all authorized proxies.

The regression creates two module contexts on one `SurfaceVm`, installs
different `this.package.id` values, then evaluates both templates and calls both
handlers after the second context exists. Before the fix, the first template
read `@mesh/second`; after the fix all four reads retain their owning module.

**Verified.** Under `nix develop`, `mesh-core-scripting` reports 179 passed / 27
ignored. The focused shell manifest-descriptor slice passes 2/2. The full shell
suite reports 569 passed / 18 failed / 122 ignored, exactly the documented
baseline with the same 18 failures by name.

## 2026-07-30 — settings values are validated, and say so

area: configuration

The single store (below) read every value with `.and_then(parse_x)`, so a wrong
type, a bad enum value, or a misspelled key produced `None` and the field kept
its default *in silence*. Unknown keys were never enumerated at all. For a file
whose whole purpose is hand-editing, that is the worst failure mode: three ways
to change nothing and hear nothing —

```json
"@mesh/navigation-bar": { "surface": { "anchr": "bottom" } },   // typo'd key
"@mesh/quick-settings": { "surface": { "anchor": "botom" } },   // bad enum
"shell": { "tooltip": { "delay_ms": "300" } }                   // wrong type
```

`docs/spec/08-settings.md` §1 already required the behavior ("rejected with a
diagnostic and the stored value is ignored"). The ignoring half worked; the
diagnostic half did not exist. All three now report namespace, key path, the
value found, and what to do, and the shell still starts on declared defaults.

**Shape.** `SettingsDiagnostic { severity, namespace, key_path, message,
suggested_action }` in `mesh-core-config`, modeled on
`ModuleManifestDiagnostic` — the `suggested_action` pairing is what makes the
manifest diagnostics actionable, and a hand-edited file needs the same. The
walk is a declarative schema (`FieldSpec` / `FieldKind`) so one implementation
serves both namespaces: `SHELL_SETTINGS_FIELDS` sits next to `ShellSettings`,
whose serde defaults define what a rejected value falls back to, and
`SURFACE_FIELDS` sits in `mesh-core-surface-config`, which owns the placement
vocabulary.

**Enum fields carry their parser, not a copy of its strings.**
`FieldKind::Enum { accepts, values }` takes `accepts: fn(&str) -> bool` — the
actual `parse_surface_edge`/`parse_keyboard_mode`/etc. — so aliases those
parsers accept (`"toplevel"`, `"csd"`, `"on-demand"`) are not reported as
errors, which a duplicated string list would have gotten wrong. `values` is the
canonical list quoted back in the suggestion, built from the `*_name` functions
(now `const fn`); `*_is_listed` guards make adding an enum variant a compile
error until its value list is updated. A test asserts every listed value
parses, so the advice a diagnostic gives always works.

**Severity.** Wrong type and bad enum are errors. An unknown key is an error
only when a known key is within typo distance (`anchr` → `did you mean
"anchor"?`, Levenshtein with a length-scaled budget so `top` is not "corrected"
to `left`); with no near match it is a warning, because it may be a
forward-looking key or one owned by a reader this walk does not know about.
Role-inert fields (`resizable` on a `role: "layer"` surface) warn rather than
error, and `promotable` surfaces are exempt entirely — they legitimately carry
both roles' fields, so anything stricter cries wolf on shipped `@mesh/settings`.

**Nothing is fatal.** `resolve_shell_settings` is now infallible: values are
checked *before* the merge, so what reaches serde is already well-typed. Before
this, `"delay_ms": "300"` failed `serde_json::from_value` and lost the whole
namespace. `set_namespace`/`merge_namespace`/`reset_namespace` dropped their
`Result` — they can no longer fail.

**Surfacing.** `resolve_frontend_module_settings` returns diagnostics rather
than logging: only the caller knows whether it is reading the store at startup
or re-reading it after a save. Live reload reports only what is new
(`new_settings_diagnostics`), so a user fixing one of five mistakes sees four,
not five again. New `mesh-shell config doctor` runs the same validation without
starting a shell — errors first, exit 1 on any error, and it also reports
orphaned namespaces (a module that is no longer installed), which closes that
separate backlog item. Against the repo's own `config/settings.json`: `no
problems found`, exit 0, asserted by a unit test as well.

**Out of scope, deliberately.** `props.*` values pass through unvalidated —
their declaration is the `<props>` block, which does not exist yet
(`docs/spec/03-components.md`); `MODULE_NAMESPACE_FIELDS` marks them `Opaque`
and the backlog carries the follow-up. The `mesh.settings` service contract
remains its own item.

Tests: 13 new in `mesh-core-config`, 12 in `mesh-core-surface-config` (bad
enum, wrong type, unknown key with and without a near match, role-inert
warning, promotable exemption, alias acceptance, clean namespace), plus a
`mesh-core-shell` guard that every accepted `tooltip.position` resolves to a
real anchor. Shell suite: 569 passed / 18 failed / 122 ignored — the same 18
failures by name as the 568/18/122 baseline, plus the new tooltip test.

`mesh-core-surface-config` now depends on `mesh-core-config`
(`docs/crate-boundaries.md` updated) for the diagnostic type and the schema
walk.

## 2026-07-30 — one settings store

area: configuration

Settings lived in four places: `config/settings-default.json` (bundled
defaults), `config/shell-settings.json` (user shell overrides), a
`config/settings.json` inside each module directory (user surface/prop
overrides written into shipped module source), and `ShellSettings.modules` for
per-module icon overrides. All four collapse into one
`config/settings.json` — `$MESH_HOME/settings.json` outside a checkout,
`MESH_SETTINGS_PATH` overriding both — keyed by namespace exactly as
`docs/spec/08-settings.md` §1 specified: `shell` for core preferences, module
ids and interface ids for everything else.

The store is **sparse**. Declared defaults live in `ShellSettings`'s serde
defaults and in each module's `mesh.surface` block; nothing copies them into
the file. `mesh-shell config eject <module-id>` materializes a module's
effective surface placement into its namespace for hand-editing, which is the
discoverability the sparse model otherwise gives up. `config path`, `config
show [namespace]`, and `config reset <namespace>` round it out.

Three things fell out of the consolidation rather than being separate work:

- **The old shell merge was lossy.** `merge_shell_settings` replaced whole
  sections, so a user file mentioning only `theme` reset tooltip and keyboard
  to whatever the defaults file said. Merging is now recursive per key; arrays
  still replace wholesale, since a pack chain or activation-key list is a
  complete ordered replacement by intent.
- **Two watchers watched one file.** `settings_watch` (shell settings) and the
  per-component `module_settings_path` poll now target the same path, so the
  per-component poll is gone: the shell reloads the store once and pushes it to
  every component through `ShellComponent::apply_settings`.
- **Keyboard input no longer touches the filesystem.** `current_keyboard_settings`
  ran two `std::fs::metadata` calls plus an mtime-keyed cache on every key press
  and release; it now reads `self.settings.shell().keyboard` off the shared
  store. This closes the backlog item "Remove filesystem metadata calls from
  keyboard events" — the fix was structural, not a new cache, so the mtime cache
  and its release microbenchmark are deleted rather than retuned.

`@mesh/navigation-bar` was storing `keyboard_mode: "on_demand"` against a
manifest declaring `"none"`. A surface that declares a `mute` keybind needs
keyboard focus by design, so that moved into the manifest as the author default
it always effectively was, rather than surviving as a user override. Its
genuine override (`i18n.default_locale: "sk"`) is the one module entry in the
new file. The other three modules' stored files held only `{"props":{"global":{}}}`
and are simply gone.

Backend provider props now read from the provider module's namespace instead of
`ShellConfig.modules` (TOML `config.toml`), which nothing populated.

**Measured.** `mesh-core-config` 20 passed; `mesh-core-surface-config` 14
passed, including round-trip proofs that an ejected block re-resolves to the
layout it was ejected from, for both layer and window roles. Shell suite: 568
passed / 18 failed / 122 ignored, against the 556/18 baseline recorded
2026-07-28 — same 18 failures, 12 additional tests passing. The whole-workspace
run is otherwise green except two pre-existing failures outside this change
(`mesh-core-animation` does not compile its tests; one `mesh-core-elements`
style-resolution test fails at HEAD).

## 2026-07-30 — runtime promotion between widget and window

area: presentation, shell, module system, styling

Phase 4 of
[`../todos/pending/2026-07-28-toplevel-window-surfaces.md`](../todos/pending/2026-07-28-toplevel-window-surfaces.md).
A live surface can now be moved between `zwlr_layer_surface_v1` and
`xdg_toplevel` without losing component state. `@mesh/settings` demonstrates it:
it opens as chrome anchored to the right edge with a "pop out" control, and once
popped out the same header shows "dock back" instead.

**The presentation layer already did the hard part.** `configure` has destroyed
and recreated the compositor object on a role change since phase 1, and the
render loop's `config_changed` already compared `last.role`. What was missing was
purely shell-side: a trigger, and dropping the cached state that describes the
object that was just destroyed. `set_surface_role` clears
`last_surface_config` and `known_surface_size` and forces a full present —
without the first, the render loop compares against the old config and never
sends the configure that creates the replacement; without the second,
`resolve_dynamic_surface_size` short-circuits on a size measured under the other
role, which is exactly wrong given the two roles size in opposite directions.

**`promotable` is a new manifest field, and it had to be.** The role-mismatch
diagnostic from phase 1 rejects layer fields on a window and vice versa, which is
right for a static role and wrong for a surface that holds both over its life —
settings needs `anchor` for its docked form and `title`/`appId` for its window
form. `"promotable": true` is the single exemption from that diagnostic, and it
doubles as the opt-in gate: a role change is refused for a surface that does not
declare it, because a root laid out as a 32px panel widget is not automatically a
sensible window. A test asserts both halves — the same manifest without the flag
is still a contradiction.

**The role is CSS state, not script state.** `:windowed` joins the four
compositor states as a fifth ambient pseudo-state (bit `1 << 17`). Settings ships
both header controls and lets `display: none` decide which exists, so the chrome
follows the surface's real role even when the role changed from outside the
component — a settings override or a compositor keybind over IPC. A component
tracking the role in a Lua variable would disagree with reality the moment that
happened. `display: none` rather than a visual hide so the inactive control is
out of layout and not clickable.

Three things worth knowing for the next surface that does this:

- **The old compositor object must be destroyed eagerly, not by `configure`.**
  This is the one real bug in the change, and only a live compositor found it.
  `configure` does swap the object on a role change, but it runs *partway through*
  the render frame — after the loop has already read `window_configured_size` and
  laid content out against it. Demotion therefore measured against the outgoing
  window's size, found its measurement already agreed with that, skipped the
  corrective configure, and left the new layer surface stranded at the 1×1 that
  the layer-shell backend clamps an unmeasured 0×0 request to. Every layer
  surface's first show sends 0×0 and relies on a second, corrected configure once
  `paint` has built the tree; a role change has to enter that same path.
  `set_surface_role` now calls `destroy_surface` itself, so
  `window_configured_size` reports `None` from that point on. Regression test
  asserts the destroy happens.
- **`observe_window_states` does not invalidate the surface config.** It
  invalidates STYLE|LAYOUT|PAINT|METRICS, so `surface_role_changed` has to add
  SURFACE_CONFIG explicitly or `render` skips `render_layout` and the
  presentation layer is never asked to swap anything.
- **The window-states projection stays keyed off the shell-surface record**, not
  the component's requested role. An earlier attempt keyed it off the component
  so a freshly promoted window would not wait a frame; that broke
  `compositor_window_states_reach_the_component_each_render` and was unnecessary
  anyway — `render_layout` updates the record the same frame, and demotion needs
  no delivery at all because `surface_role_changed` clears the states itself.

Triggers: `shell.set-surface-role` / `shell.toggle-surface-role` on the script
event channel, and `shell:promote_surface:` / `shell:demote_surface:` /
`shell:toggle_surface_role:` on the IPC line protocol. The IPC path exists
because MESH keybinds are focused-surface actions and cannot grab a global
hotkey, so a compositor binding has to shell out.

Also refused, with a diagnostic rather than silently: promoting a surface
realized as a popover (it has no independent placement, and its trigger would
point at a destroyed surface), and promoting when the compositor has no
`xdg_wm_base`. The latter is checked *before* teardown, because window creation
fails inside `configure` — after the old layer surface is gone — which would
leave the surface unmapped with no way back.

Settings' first configure is now the layer shape again (920×900: the 700px
measured root plus the 200px tooltip overlay reserve) rather than the window
shape (920×700, no reserve); `frontend_module_activation_mounts_shipped_surface_live`
was updated to match.

**Verified against live Hyprland.** Driven over IPC across
show → promote → demote → promote, with `hyprctl` as the independent check. The
configure sequence per role change is `0×0` then the corrected size, and the
sizes come out exactly as designed:

| State | Configure | `hyprctl` |
| --- | --- | --- |
| shown as chrome | 0×0 → 920×900 | `LAYER @mesh/settings 920x900` |
| promoted | 0×0 → 920×700 | `TOPLEVEL class='mesh.settings' title='Settings' size=[1429,841]` |
| demoted | 0×0 → 920×900 | `LAYER @mesh/settings 920x900` |

920×900 is the layer shape (700 measured + 200 tooltip reserve) and 920×700 the
window shape (no reserve), which is the distinction phase 1 introduced. The
promoted toplevel is tiled by Hyprland into 1429×841 — the compositor overriding
the requested size is the whole point of the sizing inversion, and the content
absorbs it through the `:tiled` rule. `app_id` and the localized title both land.
The transient `layer surface configured 0x0 … clamping to 1x1` ERROR on each
change is the pre-existing first-configure noise every layer surface logs (
`@mesh/touch-gesture-proof` does the same on show), corrected by the retry in the
same frame.

Shell suite: 566 passing, 18 failing, 123 ignored under `nix develop`. The 18 are
the same set as the 2026-07-28 baseline — verified by diffing the failure lists
with and without this change. Pre-existing and untouched: one
`mesh-core-elements` failure, two `mesh-core-module` failures, and three
`mesh-core-animation` *test-compile* errors.

**Left open.** Phase 5, per-widget promotion — promoting a widget embedded in
another surface, rather than a whole surface — still depends on the shared
surface VM and on multi-instance frontend modules. The typed `surface.*`
automation envelope and the `mesh surface toggle-role` CLI subcommand land with
the rest of spec 11; only the raw line protocol is wired today.

## 2026-07-29 — window states as CSS state

area: presentation, styling

The compositor's `xdg_toplevel` states arrived on every configure and were
logged and dropped, so a window could not tell fullscreen from floating. They
are now `WindowStates` on the presentation role, delivered to the component
through `ShellComponent::surface_window_states_changed`, and projected onto the
tree as four pseudo-states: `:fullscreen`, `:maximized`, `:activated`,
`:tiled`.

**They are carried on every node, not just the root.** The selector subset has
no descendant combinators, so a state that lived only on the surface root would
be unreachable from the elements that need it — a sidebar cannot write
`.window:fullscreen .sidebar`. Projection happens in
`annotate_runtime_tree_inner`, which already writes every node's
`ElementState`, so the cost is four bools per node and no extra traversal. The
four new state bits ride the existing `StyleRuleIndex` bit index, so candidate
lookup and matching needed no special case; the diagnostic tree fingerprint's
`state_bits` widened from `u16` to `u32` to fit them.

**Delivery sits ahead of the `wants_render` gate** in `render_components`. A
compositor state change is exactly what makes an otherwise-quiet window want to
render; asking behind the gate strands a fullscreened surface at its floating
style until something else dirties it. `observe_window_states` invalidates the
way a resize does (STYLE|LAYOUT|PAINT|METRICS, cached measurement cleared)
rather than taking the targeted interaction-restyle path — the change is
ambient and happens at human frequency.

`@mesh/settings` uses it: the floating 920×700 stays on the base rule, and
`:fullscreen`/`:maximized`/`:tiled` take `width: 100%` and clear the floating
minimum. Its `"resizable": false` is gone — pinning min to max is what stopped
the compositor resizing it in the first place, which is why a fullscreened
settings window was still a 920×700 island.

**Left open.** `min-*`/`max-*` are `Option<f32>` while `width`/`height` are
`Dimension`, so `max-width: 100%` cannot clamp a fixed root to its surface and
each filling rule must clear the floating minimum by hand. Backlog item filed
under *Tech debt*.

**Measured.** `mesh-core-shell --lib` 560 passed / 18 failed against a
stash-verified 556 / 18 baseline — the same 18 failures by name, plus the 2 new
tests and 2 real-surface tests that the settings CSS change fixed. Rest of the
workspace matches its baseline: the pre-existing failures in
`mesh-core-elements` (1), `mesh-core-frontend` (1), and `mesh-core-module` (2)
are unchanged, and `mesh-core-animation`'s test target still does not build.

## 2026-07-29 — toplevel window surfaces

area: presentation

`mesh.surface.role: "window"` realizes a frontend module as an `xdg_toplevel`
instead of layer-shell chrome. `@mesh/settings` ships as a window; panels,
launchers, and popovers are unchanged.

The role axis already existed in the presentation layer — the internal
`SurfaceRole` enum (renamed `WaylandRole`) gained a `Window` variant alongside
`Layer` and `Popup`, so the whole SHM / present / scale / damage / input path is
shared. `LayerSurfaceConfig` became `SurfaceConfig` and `LayerShellBackend`
became `WaylandSurfaceBackend`, since neither is layer-specific any more.
`XdgShell` was already bound for popup positioners; it now also drives
`create_window`, a real `WindowHandler`, and per-toplevel decoration objects.
The comment at `handlers.rs` claiming MESH never creates toplevels is gone.

**Sizing inverts, and that is the whole design.** A layer surface tells the
compositor its CSS-measured size; a window is *told* its size by the configure
and lays content out into it. `window_configured_size()` overrides the measured
size once the compositor has named one. The measured size is only the initial
request, so a resizable window deliberately publishes **no** min size —
publishing the natural size as a minimum would let a user grow a window but
never shrink it. `resizable: false` pins by reporting the content size as both
min and max.

**Three things only showed up against a live compositor** (Hyprland 0.56):

1. The tooltip overlay reserve leaked into the toplevel's pinned size — a
   920×700 settings root mapped as a 920×900 window. Windows now take no
   reserve: a toplevel's size *is* its content size, and a tooltip that must
   escape a window is an `xdg_popup`, which `<popover>` already promotes to.
2. Hiding by detaching a buffer unmaps a toplevel, and remapping needs a fresh
   configure the compositor is under no obligation to send for a commit
   carrying no new state. A re-shown window waited out the 500ms configure
   deadline every frame and never reappeared. Windows are now destroyed on hide
   and recreated on show — the lifecycle promoted popovers already use.
3. `destroy_surface` silently ignored anything that was not a layer surface, so
   fix 2 was a no-op until it was widened to all non-popup roles. Symptom: hide
   left the window mapped.

Also: layer placement fields on a window (and window fields on a layer surface)
are a `surface_role_field_mismatch` graph diagnostic rather than a silently
dropped key; `keyboard_mode` is skipped for windows, which also protects them
from the synthetic 1×1 hidden geometry; popups can be parented to a window
(`xdg_surface.get_popup`) as well as a layer surface; the user can move a
surface between roles through the sparse settings store.

**Measured.** Workspace suite 1640 passed / 22 failed, against a
stash-verified pre-change baseline of 1630 / 22 — the same 22 failures by name,
so no regressions; 10 new tests. Clippy warning count unchanged at 248.
`frontend_module_activation_mounts_shipped_surface_live` asserted the settings
surface configured at 920×900 and now asserts 920×700: that test encoded the
layer-surface geometry, and the reserve removal above is the intended change.
Note `mesh-core-render`'s lib tests are flaky under the workspace run — one
sampled run failed 8 of them and two adjacent runs failed none, in a crate this
work does not touch.
`mesh-core-animation` does not compile its test target on this tree (unrelated
pre-existing errors in `keyframes.rs` / `transition.rs`) and was excluded from
both runs. Live on Hyprland 0.56: window maps at exactly 920×700 with title
`Settings` and app id `mesh.settings`, and three hide/show cycles over the IPC
socket each destroyed and recreated it at the same size.

**Left open.** Runtime promotion between widget and window, the
`surface.promote` / `surface.demote` IPC verbs, and window states
(maximized/fullscreen/tiled) as CSS state on the root — all three are in
`docs/BACKLOG.md`. The compositor delivering `xdg_toplevel.close` was not
exercised end to end (Hyprland 0.56's Lua `hyprctl dispatch` would not accept a
window-targeted close); the shell side of it — close request drains to a hide
that keeps the component alive — is covered by two tests against the testing
backend.

## 2026-07-28 — style and composition checkpoints

`c00655ac` · area: style resolution, composition

Theme-default lowering now survives fresh `StyleResolver` construction: `Theme`
carries a monotonic style revision, and resolvers share a bounded thread-local
cache keyed by that revision, `(module_id, tag)`, and a collision-checked prop
snapshot. Indexed stylesheet declarations and theme-default maps pre-lower
static literals into typed colors, numbers, edges, corners, and dimensions;
`var()` / `prop()` values and all diagnostics deliberately retain the dynamic
string path.

Separately, the shared element IR took ownership of the embedded-handler and
component-prop wire protocol (`composition.rs`), replacing scattered magic
strings with typed constructors and constants.

**Measured.** Release, three runs of 100,000 fresh prop-bearing resolvers:
125.7–128.8ms repeated lowering versus 18.83–20.35ms through the revision cache
(6.18–6.84x). Representative 456-node tree build 0.416–0.424ms before versus
0.390–0.397ms after (1.05–1.09x end to end). Gated as
`shared_theme_defaults_speedup`.

**Left open.** Typed property values and one-time token lowering. Typed
declaration application has correctness parity coverage but its release
measurement and canonical gate were still pending at the time of the commit.

## 2026-07-28 — SHM buffers reused across content resizes

`56731a7f` · area: presentation

Wayland surfaces with `wp_viewporter` round physical SHM allocations up to 64px
size classes and crop to the rendered extent before applying the logical
destination. A six-frame content-size jitter sequence now keeps one pool
configuration instead of six. Compositors without a viewporter deliberately
retain exact-size allocations.

Newly allocated buffers begin with full visible damage, so a first sparse frame
cannot expose uninitialized pixels; the viewport crop uses post-`buffer_scale`
source coordinates, including fractional-scale frames.

**Measured.** Presentation suite: 55 passed, 12 ignored.

## 2026-07-30 — spanning layer surfaces retain their dynamic axis

area: Wayland surface layout

After a component's first CSS measurement, the shell was feeding a top or
bottom surface's measured content width back into layer-shell. Some compositors
then center that fixed-width surface despite its left/right anchors. The surface
layout bridge now keeps the anchored spanning axis at protocol size zero
(`width` for top/bottom; `height` only for docked left/right rails with a
positive exclusive zone), while retaining the measured cross-axis size for
floating side surfaces.

`nix develop -c cargo test -p mesh-core-shell
navigation_bar_keeps_layer_width_dynamic_after_css_measurement --lib` passes
alongside `floating_side_surface_keeps_its_measured_height` (2 focused tests).
The direct host Cargo invocation cannot build this crate because the host lacks
`xkbcommon.pc`; the Nix shell supplies it.

## 2026-07-30 — settings scrollbar appears only on overflow

area: settings surface

The settings page's scroll container used `overflow-y: scroll`, which painted
an idle scrollbar even when its content fit. It now uses `overflow-y: auto`,
keeping scrolling available while rendering the scrollbar only when content
actually overflows.

`nix develop -c cargo test -p mesh-core-shell
settings_scrollbar_is_conditional_on_overflow --lib` passes (1 test).
