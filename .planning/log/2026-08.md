## 2026-08-21 — Make optimistic service writes transactional

`working tree` · area: service contracts and shell state routing

Contract-bound optimistic state now records the correlated `CallId`, provider
generation, previous visible value, and desired value. Terminal failures,
timeouts, cancellation, throttled supersession, provider unavailability, and
provider replacement roll back only the transaction that still owns the field;
newer writes take ownership without allowing older completions to overwrite
them. Historical ownership chains unwind correctly when multiple writes fail,
and successful writes remain shell-visible until a matching provider snapshot
confirms them.

## 2026-08-08 — Fix the settings surface opening and closing twice

`working tree` · area: Wayland surface configure lifecycle

Two defects in the render loop's configure path, both observed live against
Hyprland with the layer list and Hyprland's `openlayer`/`closelayer` events as
the measurement.

**A configure could carry a size the protocol had to invent.** `render_layout`
writes `(0, 0)` for a component with no content measurement, and
`observe_surface_size` drops that measurement whenever the available size
changes — so a zero reached the configure on any frame between a configure and
the paint that re-measures. It also survived into the loop's second pass,
because `render` only re-runs `render_layout` while the surface config is dirty
and a component whose content measures exactly what it was laid out against
leaves it clean. On the wire zero is not "unknown" but "span the output", so
`layer_protocol_size` clamped it — for the floating settings surface, to 1x1 at
its anchor corner, logged as an error every time. The visible result was the
surface collapsing to a sliver and popping back to full size on each show and
hide: settings appearing to open twice, and to close, reopen, and close.

Configures are now held back rather than sent with a zero no anchor backs
(`layer_configure_size_is_resolved`, which mirrors `layer_surface_request_size`:
a top/bottom bar spans horizontally, a docked rail spans vertically, a window is
exempt because its size is a hint). `config_changed` stays true, so the real
geometry goes out as soon as it exists. The corrective second pass also
re-dirties the surface config now, so it re-derives the size from the
measurement the paint in between produced instead of resending the first pass's
zeros — which is also what left `@mesh/blur-test` and `@mesh/opacity-test`
permanently mapped at the 1px clamp.

**A hidden layer surface could never be shown again.** Hiding attaches a null
buffer, which returns the surface to the unconfigured state on both sides: the
backend clears `configured` and the hidden frame drops `last_surface_config`.
The render loop then waited on `surface_ready_to_present` before it would send a
configure — waiting for an event only that request can provoke. Every
`ShowSurface` after the first silently did nothing; reproduced on the live shell
before the fix (IPC show, no configure, no `openlayer`, nothing on screen). The
readiness gate now applies only to a surface whose configure has already been
sent. The present itself was always safe: it reports `NotReady` and retains the
damage.

Verification: five layer open/close cycles on the live shell, each exactly one
`openlayer`/`closelayer` pair and one configure at the measured 920x900, plus
promote-to-window, hide/show as a window, and demote back — zero protocol clamps
across the session, against three clamps and a dead reopen before. Two shell
regression tests added (reopen after unmap; no configure carries an unbacked
zero) plus a unit test for the spanning/docked exemptions.
`unconfigured_surface_keeps_pending_frame_until_configure_retry` now renders one
frame first, so it waits on an answer to a configure that was actually sent —
its old setup encoded the state the second defect made unreachable. Full
`mesh-core-shell --lib`: 666 passed, 6 failed, 128 ignored; the same six fixture
failures fail on a clean checkout of the parent commit.

## 2026-08-07 — Composition and configuration writes are capability-gated contracts

`working tree` · area: settings, module system, capabilities

Stage 1 removed the hardcoded `@mesh/settings` host from `catalog.rs`, but the
same literal survived in `service.rs`, where it was doing more damage:

```rust
"shell.set-provider" if event.source_module_id == "@mesh/settings" => ...
"shell.set-module-enabled" if event.source_module_id == "@mesh/settings" => ...
"shell.set-module-prop" if event.source_module_id == "@mesh/settings" => ...
```

Seven reserved `shell.*` channels were gated on the publishing module's **name**.
A replacement settings frontend could be mounted — Stage 1 made that structurally
possible — and then silently do nothing, because every write it issued was
dropped by a string comparison. The channels were also a contract in nothing but
name: no argument types, no capability, and no diagnostic when a payload was
wrong, since a non-matching arm just fell through to `None`.

**Writes are now methods on core-provided interfaces.** `mesh.settings` gains
`set_prop`/`unset_prop`, `mesh.theme` gains `set_theme`/`set_icon_theme`/
`set_font_family`, and a new `mesh.packages` contract carries
`set_module_enabled`/`set_provider`/`switch_profile`. These are declared like any
other contract, so they flow through the *existing* generic path: a published
`mesh.packages.set_provider` is split into interface and command, checked against
`service.packages.control`, and refused with a diagnostic naming the missing
capability. No module id is consulted anywhere in that path.

**The shell answers its own interfaces.** `dispatch_service_command` previously
knew only Luau backends, so a core interface would have returned
`service_unavailable`. It now translates a core-provided command into the
`CoreRequest` that performs it and applies it directly, pushing follow-up
requests onto `deferred_requests` — the queue a profile switch already used.
Argument extraction is strict: a payload that does not match the declared
contract yields `None` and is reported as unsupported, rather than applied with a
defaulted value.

**Two things this exposed.** `theme.write` was declared a High-privilege
capability and enforced nowhere; `shell.set-theme` was ungated, so any module
could restyle the entire shell. Theme writes now require `service.theme.control`,
and `theme.write` is deleted from the vocabulary rather than left as a second
name for the same thing. Regression:
`setting_the_theme_now_requires_a_capability`.

Conversely, `shell.set-locale` **was** correctly gated — at the host-API
boundary, where `mesh.locale.set` enforces `locale.write` before publishing.
Deleting it broke three locale tests and it was restored. A second,
service-shaped route in would have meant two capability names for one write, so
`mesh.locale` deliberately gains no method.

**Scope.** `shell.open-debug-source` is still gated on
`@mesh/debug-inspector`. That id appears at six sites in the shell (surface
identity, benchmark scenarios, profiling), so converting one of them in
isolation would have been cosmetic; it stays with the open backlog item for
moving built-in debug behavior behind generic providers.

The settings frontend's **reads** were already a revisioned `mesh.settings`
broadcast and did not change. What did not close: `publish_resolved_props` still
injects each component's namespace as a raw `settings` prop, so the backlog item
was narrowed to that rather than deleted.

Verification: `cargo test --workspace --no-fail-fast` fails exactly the same 8
tests as `c4c29292`, by name. Eight `surface::icon::tests::*` failures appeared
in one intermediate run and not the next; they pass 14/14 in isolation and are

## 2026-08-07 — Compositions are modules; extension points are contracts

`working tree` · area: module system, installation, settings

Five staged changes making a shell composition installable, updatable, and
forkable, and removing the last module id hardcoded into the shell. Design:
[`todos/pending/2026-08-07-composition-modules-and-extension-points.md`](../todos/pending/2026-08-07-composition-modules-and-extension-points.md).

**Extension points replace module-keyed slots.** `provides_slots` produced slot
ids like `@mesh/settings:custom-settings`, so every contributor named the host
and replacing the settings frontend silently dropped every contributed page.
Worse, it was structurally unusable from a manifest: the canonical loader left
`slot_contributions` empty, so the only way to fill a slot was
`const SETTINGS_HOST: &str = "@mesh/settings"` in `catalog.rs` — core policy in
the wiring layer, the `if service == "audio"` bug in a different domain.
Extension points are now versioned contracts declared by interface modules
(`mesh.extensionPoints`), hosted explicitly (`mesh.hosts`), and contributed to
by contract name (`mesh.provides.extensionPoints`). `SlotDefinition`,
`SlotContribution`, `provides_slots`, `slot_contributions`, and
`mesh.entrypoints.settings_ui` are deleted outright, not aliased. A contribution
now creates **no dependency edge on its host** — the edge terminates at the
contract — which is why `detects_cycles_through_slot_hosts` was replaced by
`host_and_contributor_are_not_a_dependency_cycle`: the adapter pattern was
previously an unloadable cycle.

**Composition modules.** `kind: "composition"` carries `mesh.compose`
(structurally a `ShellProfile` plus `slots`) and `mesh.extends`. A profile
becomes an instance: `schemaVersion: 2` adds an optional `from`, and resolution
layers base composition → derived composition → profile deltas. Two merge rules
are deliberate rather than incidental: ordered resource chains **replace** (an
icon chain is an ordered fallback list; interleaving two orderings is
meaningless), and a user override for a root the composition dropped is
**retained and reported** (`orphaned_profile_override`) rather than discarded,
since dropping it loses the user's work on every upstream rename. A composition
declares no capabilities — `composition_declares_capability` is a hard error —
or it becomes the privileged layer replaceable modules exist to avoid.

**Lock v2.** `mesh.lock` gained `version`, a `sha256` content digest over the
installed tree, `requestedBy`, and generations archived under `lock-history/`.
The digest is what makes `spec/02` §1's "updates preserve edits" enforceable
rather than aspirational; previously local edits were undetectable. Lock writes
are now transactional: `persist_git_provenance`'s warn-and-continue was right
for a one-off install and wrong for a composition, where the lock *is* the
rollback record.

**Update transaction.** `mesh update` resolves candidate revisions via
`git show <rev>:module.json` (version without checkout), diffs
`InterfaceContract`s as data to classify breakage without executing module code,
diffs capabilities for elevated/high re-approval, and refuses to overwrite
edited trees. `--dry-run`, `--keep`, `--replace`, `mesh rollback`,
`mesh uninstall` (refuses while `requestedBy` is non-empty), and
`mesh lock verify` ship with it. Rollback re-fetches by revision rather than
archiving trees, since git is already content-addressed.

**Settings-UI ladder.** composition override > module page > generated
fallback. The generated fallback is kept — without it a third-party module has
zero settings UI until someone writes an adapter, which centralizes worse than
the hardcoding being removed. A suppressed page reads as absent so the host
falls back to generated rows rather than showing nothing.

Also: version resolution over the enabled closure with a one-version-per-module-id
rule (the id is also the settings namespace and surface instance key, so two
copies would fork the settings store), `mesh.uses.sources` for fetching
uninstalled dependencies, `mesh profile prune`, and the LSP manifest schema
updated in step with every manifest change.

Verification: `cargo test --workspace --no-fail-fast -- --test-threads=1` under
`nix develop`. Failures are exactly the pre-existing baseline, each confirmed by
re-running the same suites at HEAD with the working tree stashed:
`mesh-core-config` 1 (`an_unknown_shell_section_is_reported_without_losing_its_siblings`),

## 2026-08-04 — The navigation bar was measuring a 1px stand-in surface

`working tree` · area: shell render loop, surface measurement, presentation

Reported as "the navigation bar renders half its size, the upper part is out of
bounds", and before that (2026-08-03, on KDE) as the shell exiting with `all 3
SHM buffers are busy for 1920x201 surface` with the bar off-screen. Both are the
same defect, and it reproduces on Hyprland: `hyprctl layers` showed the shipped
bar as a **1920x201** layer surface painting nothing, where 201 is 1px of
content plus the 200px tooltip reserve.

### What actually happened

A surface's first frame has no size on either axis — the compositor has not
configured it and nothing has been measured. The shell resolved that to `1` (a
buffer needs real pixels), and `finalize_tree` stamped it onto the synthetic
`surface` root as a **definite** `Px(1)` box. `.nav-shell` declares
`height: 56px`; laid out in a 1px surface it comes out 1px tall, and
`measure_content_size` faithfully reports the collapse. `render_layout` then
sends that 1 to the compositor as the bar's height — and a *nonzero* height is
no longer a dynamic axis, so `resolve_dynamic_surface_size` never consults the
compositor's real size again. The bar stays 1px of content in a 1920x201 buffer
for the life of the process, and repeatedly presenting that surface is what
saturated the three SHM buffers on KDE.

Instrumented paint on the live shell: content extent `1x1` then `1920x1`, child
style `height: Px(56.0)`, child layout height `1.0`, `measured_size=(1920, 1)`.
An isolated Taffy repro confirmed the mechanism and the shape of the fix — a
definite `Px(1)` root collapses the child to 1x1; an `auto` root axis measures
56 whatever the available space is.

### The fix

An axis with no size is not a small size. `SurfaceExtent.content` now carries
`0` for an axis the shell could not resolve, `paint` records which axes those
are, and `finalize_tree` gives the surface root `Dimension::Auto` there instead
of `Px(stand-in)`. The stand-in still sizes the buffer and the damage rects; it
just never becomes a layout box. Content measurement measures content again.

Kept from the first pass at this bug (which fixed real things but not the
cause): the first unmeasured layer configure is deferred to the immediate
re-render, so the compositor sees one configure instead of two, and a saturated
SHM pool returns `PresentStatus::NotReady` — ordinary Wayland backpressure —
instead of a fatal `BufferAlloc` that killed the process.

### Verification

Live on Hyprland: the navigation layer is **1920x256** (56 content + 200
reserve) from exactly one configure, the bar paints in full (workspaces, title,
clock, control cluster), and 25s of running produced no busy-buffer error.

`unmeasured_navigation_bar_measures_its_own_height_not_the_placeholder` paints
the shipped `@mesh/navigation-bar` with `SurfaceExtent::padded((0,0),(1,201))`
— exactly what `render_components` passes before the first configure — and
asserts 56. Reverting the `Auto` branch fails it 1 vs 56.

`mesh-core-shell` is 628 passed / 9 failed / 125 ignored: the eight documented
deterministic failures plus the documented parallel-only phase26 raster-cache
one, with the new test the only delta. `mesh-core-presentation` 64/64,
`mesh-core-elements` 210/210.

Session record: [`../debug/kde-navigation-shm-buffers.md`](../debug/kde-navigation-shm-buffers.md).

Two of the failures were **real defects**, not stale expectations.

### A dragged slider stopped repainting after the first move

`slider_drag_repaints_across_multiple_pointer_moves` was correct and the
product was wrong. A handlerless slider drag takes the targeted
interaction-restyle path, whose changed-node set
(`collect_interaction_changed_node_ids`) diffs hover, focus, focus-visible,
active, and checked. A slider value is none of those — it is *painted content*.
So the second and later pointer moves of a drag found an empty changed set,
`empty_restyle_avoided` short-circuited the frame, and the display list kept
the previous knob position. The widget tree was correct throughout: it recorded
`value="90.91"` then `value="27.27"` while the painted bytes stayed
**identical** (0 of 38,400 differed), and forcing a full tree rebuild painted
the moved knob, which is what isolated the invalidation path as the culprit.

Fixed by tracking `previous_slider_values` and diffing it into the changed-node
set. Unlike the `checked` diff it is **not** gated on
`cached_restyle_state_dependencies` — a slider repaints whether or not any
selector mentions it. All 18 slider tests pass.

`raw_service_state_update_schedules_repaint_without_proxy_tracking` rendered
`{last_service_update.name}` as `""` when the state held `"audio"`. Template
expressions are compiled to Luau closures over the context's `_ENV`, but
`seed_service_state` and `apply_service_update_*` wrote only to the Rust
`ScriptState`. Any template expression naming a host-injected global therefore
evaluated against a nil Luau global. A probe confirmed the split precisely: a
script-authored `localobj.name` rendered `LOCAL` while `last_service_update.name`,
`last_service_update`, and `audio.percent` all rendered empty from the same
build, with the correct values visible in `ScriptState` at build time.

Fixed with `seed_service_context`, which seeds the trace through
`seed_context_global` (state *and* `_ENV`), plus an `_ENV` refresh on update.
`set_with_fingerprint_lazy` now returns whether it installed the value, so the
refresh costs one JSON-to-Lua conversion only when the trace actually changed —
unchanged fan-out probes still allocate nothing. Service *payload* globals keep
their existing proxy design (`__mesh_svc_*` reached via `require`); only the
host-owned trace changed.

## 2026-08-03 — Surface reserve and input region are one decision

`working tree` · area: presentation, shell surfaces, input

The shell blocked clicks in a ~200px strip under the navigation bar again. Not
a new mistake — the twentieth instance of one structural one.

**Why it kept coming back.** MESH deliberately configures parent surfaces
*larger* than their content: `tooltip_overlay_extra_for_content` adds 200
logical pixels below a bar (and widens narrow surfaces to 352) so tooltips can
paint outside the content box, and popovers pad their buffer for descendant
shadow/filter overshoot. Those pixels are transparent, so unless the surface's
input region excludes them the compositor routes every click over them to MESH.
Inflation happened in `render_components`; confinement happened much later in
`present_surface_target`, as a separate `update_input_region` call guarded by
the `last_region_state` cache. That is fail-*open*: every way the second half
could not run — a surface entry recreated for a role swap, a window destroyed
on hide and rebuilt with `input_region_rect: None` while the shell still
believed the region was applied, a `update_input_region` dropped because the
backend had no entry yet, a present that returned before the region flushed —
reinstates the dead zone, and none of it is visible in tests because the
testing presentation backend discarded `update_input_region` entirely.

**Fix.** The reserve now travels with the size that created it.
`SurfacePadding { left, top, right, bottom }` is a field of `SurfaceConfig` and
`PopupConfig`, produced together with the inflated size by the single function
`surface_geometry_with_overlay_reserve` (returning `(w, h, padding)`, so a
caller cannot inflate a surface without saying which part is reserve).
`SurfaceEntry` derives the input region from its padding on every commit and
compares against the last committed value, so it is re-published automatically
after any entry recreation. `PresentationEngine::update_input_region` is gone;
there is no setter to forget. Both shell call sites were removed.

**Verified.** `mesh-core-presentation`: 64 pass (5 new, covering trailing
padding, ring padding, zero padding, oversized padding degrading to
whole-surface input rather than an unclickable zero-area region, and
padding participating in the config fingerprint so `apply_config` adopts it).
`mesh-core-shell`: 4 new tests — a bar surface whose input region is the
content rect, the generic invariant that every configured surface's
`size - padding` equals its content size, an uninflated window taking input
everywhere, and a padded child popup confining input to the visible popover.
Mutation check: reverting the padding to `SurfacePadding::default()` fails two
of the four. Failure set for `mesh-core-shell` is byte-identical to `main`
(20 pre-existing failures, unrelated: theme reload, slider drag, real-surface
geometry).

**Also found, not fixed.** `ShellComponent::paint` receives the *padded*
extent as `width`/`height` and falls back to it as the content size when the
surface has not been measured yet, so `last_surface_size` records the reserve
as content for one frame (probed: `content_input=(1920, 201)` on frame 0 of the
shipped navigation bar, correct from frame 1). That no longer reaches the
compositor, but it lays the first frame out against an inflated height. Making
`paint`'s fallback prefer `last_surface_size` pins the old size for direct
callers; the real fix is separate content/padded arguments. In `docs/BACKLOG.md`.

**Pre-existing breakage noticed.** `mesh-core-elements` tests did not compile
(`legacy_deep_clone` missing `loop_identity`); fixed in passing, which reveals
two genuinely failing style tests
(`indexed_theme_defaults_reuse_lowered_declarations_per_revision`,
`shipped_navigation_style_expected_diagnostics_do_not_block_tokens`) and one in
`mesh-core-frontend` (`for_node_wrapper_carries_no_padding_or_gap`). Untouched;
in `docs/BACKLOG.md`.

## 2026-08-03 — Quick settings opened as a 1px sliver

**Symptom.** Hovering the navigation bar's settings button drew a 1px-wide
vertical strip directly under the button instead of the quick-settings panel,
and the strip lingered through the hover-bridge/exit delay after the pointer
left. Measured on the live shell (Hyprland, HDMI-A-2): an opaque `#282828`
column at monitor-local `x=1877`, `y=56..329` — 1 x ~274, i.e. the panel's real
height at a width of one pixel.

**Cause.** `modules/frontend/quick-settings/src/main.mesh` styled its
`<popover>` root `.qs-shell` with `width: fit-content; height: fit-content`.
`fit-content` parses to `Dimension::Content`, which `taffy_dimension` maps to
Taffy `auto`; the synthetic surface root is a column flex container with
`align_items: Stretch` and `width: Px(available)`, so an `auto` cross size is
stretched to the available width. A promoted popover has no available width to
speak of on its first paint: `ActivatePopover` seeds `PopupPlacement.size` at
`(1, 1)`, `declared_or_measured_size()` is `(0, 0)` until something is measured,
and `paint` falls back to the surface extent — so the first layout ran at 1px,
`measure_content_size` reported 1, that became `measured_size`, and every
later frame re-measured against the same 1px. A fixed point at one pixel.
Height was never affected: `auto` on the main axis is content-driven.

**Fix.** Use `width: fit; height: fit`, the same pair the two other shipped
popover roots (`@mesh/theme-selector`, `@mesh/language-popover`) already carry
with a comment saying `<popover>` needs the fit value explicitly. `fit` is
`Dimension::Fit`, which `resolve_fit_sizing` resolves *after* layout by growing
the node to its descendants' union bounding box — so it does not depend on the
available width the popup was measured against.

**Verified.** Live, against the running shell via module hot reload: hover the
gear, the full 300px panel renders (sliders, theme and language chips); move
away, and a pixel diff of the column against the idle frame shows nothing left
at `x=1877`. Before the change the same diff flagged that column across 45% of
rows in `y=0..600`.

**Not fixed.** (1) `fit-content` silently degrading to stretch is a trap any
module can fall into — the layout report already records
`"content dimension mapped through Taffy measurement"` for it, but nothing
surfaces that as an authoring diagnostic. (2) Independently, a content-measured
popup's first layout runs against the `(1, 1)` placeholder rather than anything
resembling its output; `fit` survives that, ordinary intrinsic sizing does not.
Both in `docs/BACKLOG.md`. (3) The panel header renders "Quick" where the
template says "Quick Settings" — separate, unrelated to popup sizing, not
investigated.

## 2026-08-03 — `paint` takes the content extent and the padded extent separately

`working tree` · area: shell surfaces, layout

Follow-on to the reserve/input-region record above, which left this behind as
"also found, not fixed".

**The defect.** `ShellComponent::paint(theme, width, height, buffer, scale)`
took one extent that meant two things. The caller passed the *padded* surface —
content plus the tooltip overlay reserve — because that is the buffer being
painted into. But `paint` also used it as the fallback content size whenever
`requested_layout_size()` was still `(0, 0)`, which is the first frame of every
surface, before anything has been measured. So the shipped 1920x56 navigation
bar laid its first frame out at 1920x256 and recorded 1920x256 in
`last_surface_size`. Everything downstream that reads content size — CSS
percentage resolution, `content_input_size`, the shell's own size cache — saw
the reserve as content for that frame.

**Fix.** One argument that carries both halves rather than two positional
`u32`s that can be handed the wrong number:

```rust
pub struct SurfaceExtent { pub content: (u32, u32), pub padded: (u32, u32) }
SurfaceExtent::unpadded(w, h)          // buffer is exactly the content
SurfaceExtent::padded(content, padded) // padded clamped up to content
```

`paint`'s unmeasured fallback reads `extent.content_*`; the paint buffer reads
`extent.padded_*`. `render.rs` builds the extent from the same
`surface_geometry_with_overlay_reserve` that produces the `SurfacePadding`, so
content, padded size, and input region now all come from one call. Popups pass
`unpadded`: their `placement.size` is already the measured content.

Same shape as the `SurfacePadding` change it follows: the reserve is not a
separate number a caller can forget to account for, it is a named field of the
value that carries the size.

**Verified.** `cargo test -p mesh-core-shell --lib`: 614 passed / 21 failed /
125 ignored across three runs, and the failing set is identical name-for-name to
`main` measured in the same checkout by stashing this work (theme reload, slider
drag, real-surface geometry, debug snapshots — all in the red baseline already
listed in `docs/BACKLOG.md`). One earlier run reported 22 failed with the same
21 names, so something in that baseline is also intermittent; not chased here.
New regression
`first_paint_lays_out_against_content_extent_not_the_tooltip_reserve` paints an
unmeasured component at `SurfaceExtent::padded((1920, 56), (1920, 256))` and
asserts both the recorded content size and that a `height: 100%` root resolves
to 56, not 256. Mutation check: pointing the fallback back at `padded_*` fails
it with `left: Some((1920, 256))` — the exact figure probed on the live shell
yesterday. `cargo check --workspace --all-targets`, `cargo fmt --all`, and
`git diff --check` are clean.

379 call sites were rewritten mechanically (`.paint(&theme, w, h, …)` →
`.paint(&theme, SurfaceExtent::unpadded(w, h), …)`); all but one are tests, and
the one production caller is `Shell::render_components`.

## 2026-08-07 — Window resize repaints per configure

`working tree` · area: Shell render loop / xdg_toplevel

Interactively resizing a `role: "window"` surface stretched the whole surface —
text, borders, background fills — until the drag was released. Cause: the
compositor grabs the pointer during an interactive resize, so the window gets no
input events, and an `xdg_toplevel` configure carrying a new size did not dirty
the component. `render_components` therefore skipped the surface at its
`wants_render()` gate, no new buffer was committed, and the compositor scaled the
last committed buffer to the box it was dragging. `window_configured_size` was
only read *behind* that gate (`render/mod.rs`), so it could never open it.

existing `surface_window_states_changed` delivery, so a resize configure runs
`observe_surface_size` → `STYLE|LAYOUT|PAINT|METRICS` invalidation and the
surface re-measures and re-presents once per configure. Nothing in the
presentation layer changed; the viewport destination was already consistent with
the buffer it was attached to.

(pre-existing hover, raster, navigation-focus, profiling-baseline, and two debug
